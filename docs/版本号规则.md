# 光律工作台 · 版本号规则

> 定于 **2026-10-23**。适用于 GitHub 仓库 `twbzpngd58-beep/guanglv-workbench` 的每一次发版。
> 一句话：`VERSION` 只写 `X.Y.Z`；**Z 修问题、Y 加功能、X 是「要备份 / 迁移 / 重装 / 重新授权」**；tag 是 `vX.Y.Z`，annotated，一次性，不可移动。

## 0. 先看这三句

1. **第三段（1.3.4 → 1.3.5）**：只修问题。项目、设置、装法都不用动，点「立即更新」即可。
2. **第二段（1.3.5 → 1.4.0）**：有新功能。旧项目照常打开，旧用法不被破坏。
3. **第一段（1.x → 2.0.0）**：用户要动手——备份 / 迁移 / 重装 / 重新授权；或旧功能变少、被付费墙拦住。**纯品牌宣传、周年、竞品对标不构成 2.0。**

> 判据原句：**老用户点一次「立即更新」后，旧项目照常打开、功能不减、装法不变 → 发 1.x；一旦要迁移数据、要重装、要重新授权，或旧功能变少 / 被授权墙拦住 → 发 2.0。**

## 1. 版本号格式

- **唯一事实来源**：仓库根目录 `VERSION`，单行，末尾一个换行。
- **允许**：`^(0|[1-9]\d*)\.(0|[1-9]\d*)\.(0|[1-9]\d*)$`，即纯三段数字，如 `1.3.4`。
- **禁止**：`v1.3.4`、`1.03.4`、`1.3`、`1.3.4.1`、`1.3.4-beta.1`、`1.3.4+build.7`、日期版本（`20261023`）、空号占位（`1.3.x`）。
- **为什么这么严**：更新比较器在**用户已经装好的旧代码**里（`backend/app.py` 与 `scripts/apply_update.py` 各一份 `version_key()`），都只取数字段、最多 4 段：
  - `1.4.0-beta.1` 会被算成 `(1,4,0,1)`，**比正式 `1.4.0` 还大**；用户会「永久升不到正式版」或更新中途失败。
  - `1.3.4.1` 占掉第 4 段，等于一个「比 1.3.4 新、但永远没有正式版」的版本。
  - 前导零 `1.03.4` 与 `1.3.4` 同键，两个 tag 会判成同一版。
- **同步位置**（发版前必须一致，`version_guard.py --check` 会逐项检查）：
  - `VERSION`
  - `README.md` 的「当前版本 vX.Y.Z」
  - `frontend/package.json` 的 `version`（Vite 会把它注入前端常量）
  - `build-baseline.json` 的 `version`（以及 `buildId / asset / asset_sha256` 与 `frontend/dist` 对齐）
  - `backend/app_versions.py` 的 `RELEASE_NOTES["X.Y.Z"]`（工作台「本版更新」读它；缺了会显示「未登记」；**从 1.3.4 起每条还要有 `category`**，历史版本不回填）

## 2. 判号：什么时候 1.3.5，什么时候 1.4.0，什么时候 2.0

### 2.1 判断顺序（先大后小，混合就高不就低）

| 顺序 | 条件（满足任一） | 新号 |
|---|---|---|
| 1 | 从任意 1.x 一键更新后，老用户的「**数据 / 装法 / 核心工作流**」至少一项被破坏：旧项目打不开或必须迁移；不能一键更新、必须重装；七步主干被替换或删除 | **2.0.0** |
| 2 | 更新后旧功能变少，或原有功能被新的授权 / 订阅 / 付费墙拦住（功能集合收缩） | **2.0.0** |
| 3 | 企业版 / 白标 / 托管版作为**独立产品线**发布：独立分发流、1.x 无法一键到达、默认入口或授权模型与主产品不同（需 owner 明确签字） | **2.0.0** |
| 4 | 用户能感知的**新能力、新模块、新工作流、新集成**，旧项目与旧用法向后兼容 | **1.Y.0**（minor） |
| 5 | 只修问题：bug、文案 / 样式、性能、更新链路稳定性、依赖安全补丁、文档修正 | **1.x.Z**（patch） |

- 一次发布里既有新功能又有修复 → **按 minor 发**；既有不兼容又有新功能 → **按 major 发**。
- **新功能不许压成 patch**：patch 的隐含承诺是「可以无脑点更新」，把功能塞进 patch 等于骗用户跳过发布说明。
- **纯文档 / 纯注释 / 纯内部脚本**：不单独发版，随下一次功能或修复带走；确实必须单独发时，算 patch。
- **hotfix 不加后缀**：不写 `1.3.5-hotfix.1`、不写 `1.3.4.1`。当天连发两个修复，就是 `1.3.4`、`1.3.5`。

### 2.2 2.0.0 的硬门槛

2.0.0 只能因为上面第 1、2、3 条发；发布说明必须逐条回答：

1. **迁移**：老项目 / 老 SQLite 能不能自动升？要不要先备份？升完还能不能用？
2. **兼容**：旧安装方式、旧 `.env`、旧书签 / 旧外壳链接还通不通？不支持就直说「必须重装」。
3. **回退**：退回 1.x 之后，新数据会不会丢？回退入口是什么？

**明确不算 2.0**：纯品牌 / 周年 / 宣传、竞品对标、「功能攒够一年」、「这次改动很大」。同仓库发布、只换 logo 或 `.env` 开关的白标属于 1.x；它若真影响现有用户（要重新授权），按第 2 条走 2.0。

### 2.3 真实场景判号

| 场景 | 判号 | 理由 |
|---|---|---|
| 修设置页刷新 bug、修导出 bug、改文案样式 | patch | 只修不增 |
| 一键更新、功能清单、本机版本回退、外壳 v2（历史 1.3.2 那批） | **1.4.0** | 新能力，旧项目照常 |
| 新增 KNX 工程包（多一条交付物，旧流程不变） | **1.4.0** | 新模块；改成「以 KNX 为中心」才 2.0 |
| 删除旧壳 `?shell=old`，且上一版已公告 deprecate 一个周期 | **1.4.0** | 有替代路径；不公告直接删 → 2.0 |
| SQLite 表结构不兼容，需要迁移脚本 | **2.0.0** | 数据被破坏 |
| 加 AI 识图，不填 key 时仍走本地几何、旧行为不变 | **1.4.0** | 新能力，默认向后兼容 |
| 企业版只换 logo / 改 `.env`，同一安装包 | **1.4.0** | 不是独立产品线 |
| 企业版独立安装包 + 独立授权校验，未授权时核心功能不可用 | **2.0.0** | 独立分发流 + 功能被授权墙拦住 |
| 只改 README 的错别字 / 内部脚本注释 | 不发版 | 不打扰用户；随下一版带走 |

## 3. 递增与序列

- 每次**发布**只在旧号基础上 +1 一个号段，低位置零：`1.3.3 → 1.3.4` / `1.3.4 → 1.4.0` / `1.4.0 → 2.0.0`。
- **不重号、不降号、不复用**已发布号；同一个号永远不会发第二次。
- **默认连续**。确需跳号（如某个号已内部占用但从未发布），只允许**同段位内**跳（`1.3.3 → 1.3.5`、`1.4.0 → 1.6.0`），**跳过的号永久作废、不得补发**；GitHub Release 正文必须写一行原因。跨段乱跳（`1.3.3 → 2.0.1`）不允许。
- **发错号只能前进**：号发小了，下一次直接发更大的正确号段；号发大了，下一次发更大的 patch；**不移动、不删除、不重打 tag**。旧 Release 保留，标题加「⚠️ 号错误」说明。
- 多个改动合并为一次发布时，按**最高**级别取号。
- **改号时机**：在构建发行包和打 tag **之前**改；tag 一旦推送，版本号永久占用。未发布的草稿号可以在发布前改回连续号。

## 4. tag 与 GitHub Release

- tag 固定写成 `v` + `VERSION`，去 `v` 后逐字相等。例：`VERSION=1.3.4` → `v1.3.4`。
- **必须 annotated tag**：
  ```bash
  git tag -a "v1.3.4" -m "光律 v1.3.4 · 一句话主题"
  ```
- **一个 tag 对应一个 Release**；tag 不可移动、不可删除、不可重打。历史 lightweight tag 只登记、不重打（见 §10）。
- **快照 tag 永不 push**：本机版本库的 `v1.3.3-20261023-183331-…` 不是发布版本；它的数字段会被更新器误判成「更新的版本」。只单推 `vX.Y.Z`，不要 `git push --tags`。
- **Release 资产固定 4 件**（文件名精确匹配，大小写敏感）：
  - `guanglv-workbench-<VERSION>.tar.gz`（唯一一个）
  - `SHA256SUMS.txt`（里面写的就是上面这个包）
  - `apply_update.py`
  - `guanglv-update.command`
- **先传齐 4 件再 Publish**：Release 已发布但资产没传齐时，用户点「立即更新」会报 409 / 没有可安装包。
- **资产重传边界**：同一个 tag 只允许重传**字节完全相同**的包（例如补传漏掉的资产、修 Release 说明）。包字节一变（哪怕只改一个字符）就必须发新 patch；`SHA256SUMS.txt` 必须和包一起核对。
- **不要勾 prerelease**（见 §5）。
- **Release 标题**：`光律 vX.Y.Z · 一句话人话`。
- **Release 正文最少 5 段**（模板见 §9）：本版重点 / 怎么升级 / 数据安全与回退 / 校验 / 已知问题（没有就写「无」）。
- **发布顺序**：`/releases/latest` 按发布时间取，不按版本号。不要事后补发跳过的旧号，否则 latest 会退回旧号，新版本对所有人隐形。

## 5. 预发布与内测

**本仓库禁止预发布号**：`VERSION`、tag、Release 资产名里都不许出现 `-beta`、`-rc`、`+build` 或第四段。

原因不是保守，是现有更新器物理上不支持（详见 `backend/app.py` 的 `version_key()` / `_latest_tag()` 与 `scripts/apply_update.py`）：

- `1.4.0-beta.1` → `(1,4,0,1)`，比 `1.4.0` 大：装过 beta 的人**永久升不到正式 1.4.0**。
- `_latest_tag()` 会永久选中 beta tag，正式 Release 之后还会提示 beta。
- beta 若漏勾 prerelease，1.3.x 用户会被一键装进测试版。

**内测合法做法**：

1. `VERSION` 写**下一个正式号**（例如即将发 1.4.0，就写 `1.4.0`）；
2. 用 `buildId` + 本机快照 tag 区分是哪次构建；
3. 只做本地包（`--tarball` 支路），**不打 tag、不发 Release**；
4. 测试机先备份 / 留快照，出问题用「光律-回退版本.command」退回。

**给用户的试新说法**（只写一次）：光律不发测试版；想先试，在备用机装新包确认无误再更主力机；出问题双击「光律-回退版本.command」。

**将来若要放开**：必须先改两份 `version_key()`、`_latest_tag()`、`update_check`、`wait_health` 与 `build_release` 校验，并补单测，再改本规则；只改文档不算。

## 6. 三个「版本」各管什么

| 标识 | 例子 | 用途 | 是否进 GitHub |
|---|---|---|---|
| 对外版本号 | `v1.3.4` | 用户看到的版本；更新器唯一消费的版本 | 是（tag + Release） |
| buildId | `eda4330a6f29` | 同一个版本号下具体是哪次构建（重传 / 热修后判断「你的包和我一样吗」） | 随 `build-baseline.json` 进仓库 |
| 本机快照 tag | `v1.3.3-20261023-183331-v1.3.3-final` | 本机回退点，不是发布版本 | **否，永不 push** |

报障时请让用户提供「版本号 + buildId」；要回退时再要快照 id。快照 id 里的版本号只是前缀，不要当成对外版本。

## 7. 发版流程（维护者必做）

### 7.1 改前

1. 本机快照（回退底线）：
   ```bash
   bash "光律版本库/scripts/version_snapshot.sh" \
     --tag "pre-github-release-<新号>" --note "发版 v<新号> 前"
   ```
2. 在**干净的**发布工作副本（git clone）里操作。先看：
   ```bash
   git status --short
   git log --oneline -3
   ```
   工作区有旧版残留时不要 `git add -A` 直接提交——会把旧文件带回去。

### 7.2 改号与说明

```bash
cd guanglv-workbench-1.3.2
python3 scripts/version_guard.py --bump patch      # 或 minor / major
# 手工补 backend/app_versions.py 的 RELEASE_NOTES（每条带 category）
# 手工写 Release 说明（模板见 §9）
```

- 改了前端：`cd frontend && npm run build && cd ..`，再 `python3 scripts/version_guard.py --baseline`。
- 只改后端：也建议跑一次 `--baseline`，让 `build-baseline.json` 的 version 跟上。

### 7.3 校验与打包

```bash
python3 scripts/version_guard.py --check --strict
python3 scripts/version_guard.py --check-bump --base <上一个已发布号>   # 发版仓库里可省 --base
python3 scripts/build_release.py
```

- `--check --strict` 任一项失败 → 不许打包。
- `build_release.py` 内部会再跑一遍版本检查，失败时 `dist-release/` 一个文件都不生成。

### 7.4 提交、tag、推送

```bash
git add -A && git commit -m "v<新号>：<一句话>"
git tag -a "v<新号>" -m "光律 v<新号> · <一句话>"
python3 scripts/version_guard.py --check-tag "v<新号>"
git push origin main "v<新号>"
```

- `--check-tag` 会检查：tag 形状、annotated、指向当前 HEAD、`HEAD:VERSION` 与工作区一致。
- 只推这一个 tag；**不要** `git push --tags`。

### 7.5 GitHub Release

1. 用该 tag 新建正式 Release（**不要勾 prerelease**）。
2. 标题：`光律 v<新号> · <一句话>`。
3. 上传 `dist-release/` 的 4 个资产；先传齐，再 Publish。
4. 正文按 §9 模板写；`已知问题` 没有也写「无」。

### 7.6 发后

1. 用**上一版**装机，走一次「设置 → 检查更新 → 立即更新」；确认版本号、项目、产品、上传文件都还在。
2. 本机快照：
   ```bash
   bash ".../version_snapshot.sh" --tag "github-v<新号>-released" --note "已发布 GitHub v<新号>：..."
   ```
3. 在 `光律版本库/history.tsv` 的备注里写清 tag、buildId、资产校验结果。

## 8. 机器强制

### 8.1 `scripts/version_guard.py`

| 命令 | 检查 | 失败后果 |
|---|---|---|
| `--check [--strict]` | VERSION 格式；README / package.json / build-baseline 的版本一致（`--strict` 把 baseline/dist 不一致也算失败）；`RELEASE_NOTES` 有当前版本（1.3.4 起每条有 `category`）；`dist/index.html` 的 asset 与 baseline 配对、sha256 一致；版本规则文件存在 | 非 0，禁止打包 |
| `--check-bump [--base]` | 新版本必须大于上一个已发布 tag / 指定 base；只能 +1 一个号段（跳号 warning）；不能低于任何已有 tag（防补发旧号）；`RELEASE_NOTES` 的 category 与 bump 类型同调（patch 不许 feat/breaking，minor 不许 breaking） | 非 0 |
| `--check-tag <tag>` | tag 必须是 `vX.Y.Z`、annotated、指向 HEAD、`HEAD:VERSION` == 工作区 VERSION、且 == `VERSION` | 非 0 |
| `--bump major\|minor\|patch` | 改 VERSION + README + package.json，打印后续步骤 | 只改这三处 |
| `--baseline` | 前端构建后，按 `frontend/dist` 重写 `build-baseline.json` | 覆盖基线文件 |

### 8.2 其它强制点

- **`build_release.py` 前置**：调用 `check_release_files()`，失败直接退出，不生成任何发行文件。
- **GitHub Actions**（`.github/workflows/version-guard.yml`）：push tag 时跑 `--check` + `--check-tag` + `--check-bump`；push main 时跑 `--check`。CI 是**事后哨兵**（tag 已经推上去了），真正的拦截在本地 `--check` 和 `build_release`。
- **语义判定不交给脚本**：patch / minor / major 的最终判断由发版人按 §2 签字，并在 Release 正文写「版本类型 + 依据」；脚本只校验格式、一致性、category 枚举。
- **`docs/发版检查单.md`**：每次发版逐项打勾，三问必答。

## 9. 发版说明模板

### 9.1 GitHub Release 正文

```markdown
## 光律 vX.Y.Z · <一句话人话>

**版本类型**：patch / minor / major
**依据**：<一句话，按 §2 的判据>

**本版重点**
- ……
- ……

**怎么升级**
- 已在 v<上一版>：设置 → 版本与更新 → 检查更新 → 立即更新
- 1.3.1 及更早：下载本页 `guanglv-update.command`，双击运行

**数据安全与回退**
只覆盖程序与前端；`data/` 与 `.env` 不动；更新前自动备份。
回退：双击桌面「光律-回退版本.command」，或版本库 `version_rollback.sh --to <id>`。

**校验**
`shasum -a 256 -c SHA256SUMS.txt`（附包大小 / 文件数）

**已知问题**
- 无
```

- patch 可把「数据安全与回退」并成一段；minor / major **必须分开写**迁移与兼容。
- 2.0.0 额外写「迁移 / 兼容 / 回退」三件套，缺一段不许发。

### 9.2 工作台内「本版更新」（`RELEASE_NOTES`）

- 键必须等于 `VERSION`，否则设置页显示「未登记」。
- **从 1.3.4 起**每条必须有 `category`（1.3.2 / 1.3.3 历史条目保持原样，不回填）：
  - `fix`：修复
  - `feat`：新功能（patch 版本里出现 → `--check-bump` 失败）
  - `breaking`：不兼容（minor / patch 里出现 → 失败）
- `title` ≤ 12 字，`detail` 1–2 句；与 GitHub Release 同源同版本键（详版在 Release，精简版在应用内）。

## 10. 历史注记（追认，不重打）

| 已发布 | 事实 | 按新规「本应」 | 处理 |
|---|---|---|---|
| `v1.0.0` | 首个开源版 | 1.0.0 | 追认 |
| `v1.3.1` | 去登录成单机、空库启动、检查更新、二维码 | 1.1.0（minor） | 追认，不重打 |
| `v1.3.2` | 一键更新 + 功能清单 371 编号 + 外壳 v2 根入口 + 本机回退 | 1.4.0（minor） | 追认，不重打；记为「本应 minor 的样本」 |
| `v1.3.3` | 只修设置页刷新 + 更新脚本健壮性 | 1.3.3（patch） | 追认，号不变 |

- 历史 tag 一律不移动、不删除、不重打：已装机用户靠这些 tag 找更新，重打会让更新链路、Release 资产、用户手上版本三条线对不上。
- 历史 lightweight tag（`v1.3.2`、`v1.3.3`）只登记为遗留；从下一个版本起必须 annotated。
- 没有 `v1.3.0`；不补。

## 11. FAQ

**Q：下次只修一个 bug，是 1.3.4 还是 1.3.5？**
A：1.3.3 之后第一个修复是 **1.3.4**；第二个修复才是 **1.3.5**。不跳号；确需跳号按 §3 写原因。

**Q：加了新功能，能不能先发 1.3.5，等攒多了再 1.4.0？**
A：不能。新功能必须 minor（1.4.0）；patch 只修不增。小步快跑就「多个功能合并发一次 minor」，而不是塞进 patch。

**Q：2.0 能不能为了宣传发？**
A：不能。2.0 是用户信任凭证；纯营销发 2.0 会让真正的断裂没人当回事。

**Q：发错号了怎么办？**
A：只能前进。号发小 → 下一次发更大的正确号段；号发大 → 下一次发更大的 patch；不移动 / 不删除 tag，旧 Release 标注号错误。不要删 Release（会让 latest 回落）。

**Q：包传错了能重传吗？**
A：只有**字节完全相同**的包可以同 tag 重传；包一变就发新 patch。`SHA256SUMS.txt` 必须同步。

**Q：为什么不能发 beta / rc？**
A：现有更新器把 `1.4.0-beta.1` 算成比 `1.4.0` 大，装过 beta 的用户永久升不到正式版；详见 §5。内测走同 VERSION 本地包 + buildId + 快照。

**Q：快照 tag 能 push 到 GitHub 吗？**
A：不能。快照 tag 里的日期数字会被更新器误判成更大的版本。GitHub 上只允许 `vX.Y.Z`。

**Q：只改文档要不要发版？**
A：不单独发；随下一次修复或功能带走。确实必须单独发时算 patch，并在 Release 正文写「仅文档」。

**Q：patch 到 1.3.10 会不会比较错？**
A：不会。`1.3.10` → `(1,3,10)`，比 `1.3.9` 大；但脚本排序必须按数字段，不能按字符串（`git tag | tail` 不可用）。
